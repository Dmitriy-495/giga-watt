# CHECKPOINT 001-001 — Foundation

## Назначение итерации

Создать первый рабочий слой цифрового двойника предприятия: организационную
структуру, сотрудников, должности, штатную структуру и объекты
эксплуатации — с прозрачной SQL-first моделью данных и минимальным
backend/frontend, достаточным для работы с этой моделью.

---

## Выполненные работы

### Организационная структура

- Фиксированная иерархия `Учреждение → Филиал → ЖКС → ПУ` реализована
  через self-reference `organization_units.parent_id` и триггер
  `validate_organization_unit_hierarchy`, проверяющий, что тип родителя
  соответствует ожидаемому уровню (1:N на каждом уровне).
- Обязательные и дополнительные реквизиты организационной единицы
  (наименование, местоположение, адрес, координаты, телефон, e-mail,
  руководитель — ссылка на сотрудника).
- Backend-модуль `organization`: List/Get/Create/Update.

### Сотрудники и штатная структура

- Справочник должностей (`positions`) — независимый редактируемый
  справочник, полный CRUD, защита от удаления используемой должности.
- Сотрудники (`employees`): ФИО, дата рождения и пол (необязательные),
  автогенерация сокращённого ФИО из фамилии и инициалов
  (`Иванов И. И.`).
- Телефоны и e-mail сотрудников (1:N), не более одного основного
  контакта каждого типа — обеспечено частичными уникальными индексами
  в БД (`uq_employee_phones_primary`, `uq_employee_emails_primary`), а
  не только в backend.
- Кадровые назначения (`employee_assignments`): связь сотрудник ↔
  организационная единица ↔ должность, тип назначения (основное,
  совместительство, временный перевод, совмещение), поддержка
  нескольких назначений одного сотрудника (история + текущее).
- Штатные единицы (`staff_positions`): организационная единица +
  должность + количество.

### Объекты эксплуатации

- Справочники типов (`object_types`) и назначений (`object_purposes`)
  объектов — оба редактируемые, назначение привязано к типу (составной
  FK + фильтр `?object_type_id=` в API).
- Сущность объекта эксплуатации (`operational_objects`): единая для
  зданий, сооружений, сетей и т.п. — без отдельных сущностей под каждую
  физическую природу объекта.
- Объект эксплуатации может принадлежать только ПУ — проверяется
  триггером `validate_operational_object_owner` (по аналогии с
  триггером иерархии организационных единиц).

### Backend

- Модули (`backend/modules`): `organization`, `position`, `employee`,
  `staffposition`, `objecttype`, `objectpurpose`, `operationalobject`.
  Каждый — model/repository/handler, SQL-first через pgx, без ORM.
- Нарушения ограничений БД (FK, CHECK, кастомные триггеры) переводятся
  в понятные сообщения клиенту (HTTP 422), а не выдают сырые ошибки
  Postgres.
- CORS-мидлварь для локальной разработки frontend (`HTTP_ALLOW_ORIGIN`).

### Frontend

- Страницы списков (read-only) для всех сущностей Foundation:
  организационная структура (с иерархией), должности, сотрудники,
  штатные единицы, типы и назначения объектов, объекты эксплуатации.
- Главная страница — навигация по разделам + проверка связи с backend.

### База данных

- Миграции `000001_bootstrap` … `000005_operational_objects_ownership`
  применяются на чистой локальной БД без ошибок (`golang-migrate`).
- Ключевые предметные правила защищены на уровне БД, а не только в
  backend-коде:
  - иерархия организационных единиц (триггер);
  - принадлежность объекта эксплуатации ПУ (триггер);
  - соответствие назначения объекта его типу (составной FK);
  - не более одного основного телефона/e-mail на сотрудника (частичные
    уникальные индексы).

## Принятые архитектурные/предметные решения

См. `docs/iterations/001-foundation/NOTES.md` (Decision Log) — в
частности:

- ПУ — единственный владелец объектов эксплуатации; остальные уровни
  организационной структуры собственных объектов не имеют.
- Здание, сооружение и другие физические сущности не выделяются в
  отдельные таблицы — все они являются объектом эксплуатации.
- Иерархия организационных единиц и принадлежность объектов эксплуатации
  ПУ защищены триггерами БД, а не только в backend.
- Сотрудник может существовать без штатной единицы.
- Должность — самостоятельный справочник, не хранится в сотруднике
  напрямую.

## Текущее состояние проекта

Полный CRUD для всех сущностей Foundation проверен вручную (curl и
браузер через Nuxt dev-сервер):

- организационная иерархия (валидные и невалидные переходы между
  уровнями);
- сотрудники, включая обязательные/необязательные поля, автогенерацию
  short_name, переключение основного телефона/e-mail;
- кадровые назначения, включая нарушения дат/типов/ссылок;
- штатные единицы;
- типы/назначения объектов, включая соответствие назначения типу;
- объекты эксплуатации, включая проверку владения ПУ.

`go build`, `go vet`, `gofmt -l` — чисто.

## Известные ограничения

- Down-миграции по-прежнему отсутствуют (см. CHECKPOINT_000-001).
- Frontend — только read-only списки без форм создания/редактирования;
  вся проверка бизнес-правил велась через API напрямую (curl).
- Нет автоматических (Go) тестов — вся проверка ручная, через реальную
  БД и HTTP-запросы.
- Нет пагинации в списках (не требовалась при текущем объёме данных).
- object_types/object_purposes проверялись с двумя типами
  (Коммунальный объект, Объект ЖФ) без "Объект КЖФ" — модель поддерживает
  любые значения справочника, добавление третьего типа не требует
  изменений кода.
