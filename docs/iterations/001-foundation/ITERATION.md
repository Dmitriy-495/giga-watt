# Iteration 001 — Foundation

## Mission

Создать первый рабочий слой цифрового двойника предприятия:

- организационную структуру;
- сотрудников;
- должности;
- базовую штатную структуру;
- объекты эксплуатации.

Главная цель итерации — сформировать прозрачную цифровую модель предприятия,
отражающую его фактическую организацию и эксплуатационную структуру.

---

## Organizational Structure

Организационная структура имеет фиксированную иерархию:

```text
Учреждение
    │
    └── Филиал
          │
          └── ЖКС
                │
                └── ПУ
Учреждение

Верхний уровень организационной структуры.

Филиал

Укрупнённая организационная единица внутри Учреждения.

ЖКС

Укрупнённая организационная единица внутри Филиала.

ПУ

Производственный участок.

ПУ является одновременно:

организационным подразделением;
территориальной единицей;
эксплуатационной единицей.

В одном ЖКС может находиться несколько ПУ.

Только ПУ непосредственно эксплуатирует объекты эксплуатации.

Organization Unit Attributes

Для каждого уровня организационной структуры предусматриваются:

Наименование;
Местоположение — населённый пункт или иное укрупнённое описание;
Адрес;
Координаты для привязки к местности;
Телефон;
E-mail;
Руководитель.

Руководитель является сотрудником предприятия.

Сотрудники могут быть связаны с любой организационной единицей:

Учреждением;
Филиалом;
ЖКС;
ПУ.
Employees

Сотрудник является самостоятельной предметной сущностью.

Обязательные реквизиты:

Фамилия;
Имя;
Отчество;
ФИО сокращённое.

Сокращённое ФИО формируется автоматически из фамилии и инициалов.

Должность не является реквизитом самого сотрудника: сотрудник не хранит
название должности напрямую (см. Positions), должность появляется через
кадровое назначение (см. Employee Assignments). Сотрудник может
существовать без единого кадрового назначения — это допустимое состояние
(см. Foundation Hardening, уточнено 2026-08-15: до этой правки формулировка
ошибочно перечисляла "Должность" как обязательный реквизит сотрудника,
что противоречило штатной модели ниже).

Дополнительные реквизиты:

Дата рождения;
Пол;
Телефоны;
E-mail.

Дата рождения и пол не являются обязательными.

Телефоны и e-mail реализуются как отдельные отношения один-ко-многим.

Для каждого типа контакта допускается основной контакт.

Employee Assignments

Сотрудник связан с организационной единицей через отдельную промежуточную сущность кадрового назначения.

Это необходимо для поддержки реальных кадровых ситуаций:

основное назначение;
совместительство;
временный перевод;
совмещение;
кадровая история.

Один сотрудник может иметь несколько назначений.

Кадровое назначение содержит:

сотрудника;
организационную единицу;
должность;
тип назначения;
дату начала;
дату окончания.

Полноценная связь назначения со штатной единицей может быть добавлена
по мере развития штатной структуры.

Positions

Должность является отдельным редактируемым справочником.

Сотрудник не хранит название должности непосредственно.

Назначение сотрудника связано со справочником должностей.

Staff Structure

Штатная структура является самостоятельной областью модели.

Штатная единица связана с:

организационной единицей;
должностью;
количеством единиц.

На начальном этапе сотрудники могут существовать без привязки
к конкретной штатной единице.

Это позволяет начать моделирование предприятия без необходимости
сначала полностью формализовать штатное расписание.

В дальнейшем штатная структура может быть расширена без изменения
базовой сущности сотрудника и кадровых назначений.

Operational Objects

Физические объекты предприятия моделируются единой сущностью:

Объект эксплуатации.

Не создаются отдельные сущности:

здание;
сооружение;
сеть;
котельная;
скважина.

Все они являются объектами эксплуатации.

Конкретный характер объекта отражается его наименованием,
типом и назначением.

Operational Object Ownership

Объект эксплуатации принадлежит ПУ.

Другие уровни организационной структуры:

Учреждение;
Филиал;
ЖКС;

не имеют собственных объектов эксплуатации.

Они являются укрупнёнными организационными единицами.

Object Types

Тип объекта является редактируемым справочником.

На старте предусмотрены базовые значения:

Коммунальный объект;
Объект ЖФ;
Объект КЖФ.

Список не является закрытым.

Система должна позволять добавлять и редактировать типы объектов.

Object Purposes

Назначение объекта является отдельным редактируемым справочником.

Для удобства выбора и фильтрации назначение связано с типом объекта.

Таким образом, при создании или редактировании объекта список доступных
назначений ограничивается выбранным типом объекта.

Для коммунальных объектов могут использоваться, например:

котельная;
скважина;
тепловые сети;
сети ХВС;
сети ГВС;
сети водоотведения;
сети НО;
кабельные сети.

Этот перечень не является фиксированным и может изменяться пользователем.

Experimental Production Unit

На этапе эксперимента используется ПУ, в котором отсутствуют:

коммунальные объекты;
объекты ЖФ;
объекты КЖФ.

Модель при этом изначально должна поддерживать все три типа,
поскольку они являются частью предметной модели предприятия.

Architectural Restrictions

В рамках Iteration 001:

не вводить произвольную иерархию организационных единиц;
не вводить отдельные сущности для зданий и сооружений;
не превращать типы и назначения объектов в жёсткие enum;
не создавать универсальный кадровый движок;
не реализовывать полноценный HR-контур;
не моделировать процессы, не необходимые для текущей предметной области;
не вводить дополнительные абстракции без подтверждённой потребности.
Completion Criteria

Iteration 001 считается завершённой, когда:

Реализована фиксированная организационная иерархия.
Для организационных единиц доступны обязательные реквизиты.
Реализован справочник сотрудников.
Реализован справочник должностей.
Реализована связь сотрудников с организационными единицами.
Реализована промежуточная модель кадровых назначений.
Поддерживаются несколько назначений одного сотрудника.
Реализованы телефоны и e-mail сотрудников.
Реализована базовая модель штатных единиц.
Реализован справочник типов объектов.
Реализован справочник назначений объектов.
Назначение связано с типом объекта.
Реализована сущность объекта эксплуатации.
Объект эксплуатации может принадлежать ПУ.
Модель позволяет работать с коммунальными объектами, объектами ЖФ
и объектами КЖФ.
Миграции проходят проверку.
Backend предоставляет API для работы с Foundation.
Frontend предоставляет базовый интерфейс Foundation.
Создан CHECKPOINT итерации.
Документация соответствует фактическому состоянию системы.
