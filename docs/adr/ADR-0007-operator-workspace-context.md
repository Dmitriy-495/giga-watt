# ADR-0007 — Operator Workspace and Organizational Context

## Status

Accepted

## Date

2026-08-15

## Context

Foundation Iteration сформировала техническую основу Giga Watt и API предметных сущностей.

Следующий этап должен перейти от технического отображения данных к рабочему интерфейсу оператора.

Оператор является пользователем Платформы и одновременно сотрудником предприятия.

Поэтому стартовый экран должен определяться положением оператора внутри организационной структуры предприятия.

Не требуется заставлять оператора начинать работу с просмотра полного дерева предприятия.

## Decision

Стартовый экран строится вокруг текущего организационного контекста оператора.

Контекст определяется через:

```text
User
    ↓
Employee
    ↓
Employee Assignment
    ↓
Organization Unit
    ↓
Operator Workspace
```

Workspace текущего подразделения является основной рабочей областью приложения.

## Application Shell

Основная структура интерфейса:

```text
Header
Breadcrumbs
Workspace
```

Breadcrumbs располагаются непосредственно после Header.

## Breadcrumb Navigation

Организационная иерархия отображается через breadcrumbs.

Для текущего подразделения:

```text
Учреждение → Филиал → ЖКС → ПУ
```

Breadcrumbs выполняют две функции:

1. показывают текущее положение оператора;
2. обеспечивают навигацию по организационной иерархии.

Родительские элементы breadcrumbs позволяют перейти в рабочий контекст соответствующего подразделения.

Текущий уровень является текущим контекстом.

Полное дерево предприятия не является обязательной частью стартового интерфейса.

## Operator Workspace

Workspace показывает информацию и доступные действия для текущего организационного контекста.

На первом этапе из workspace должны быть доступны существующие Foundation-области:

- сотрудники;
- штатная структура;
- объекты эксплуатации.

Workspace не должен превращаться в универсальный dashboard framework.

## Multiple Assignments

Employee может иметь несколько назначений.

В рамках Iteration 002 не вводится универсальный механизм автоматического выбора между несколькими назначениями.

Для первого рабочего сценария текущий контекст должен быть однозначно определён.

Поведение для нескольких действующих назначений является отдельным предметным вопросом следующей итерации.

## Current User

Authentication пока не реализуется.

Frontend должен работать с контрактом текущего оператора, а не зависеть от конкретного будущего механизма authentication.

Временный механизм определения текущего пользователя допускается в рамках Iteration 002.

Этот механизм должен быть явно обозначен как временный и не должен формировать будущую архитектуру authentication.

## Frontend Principles

Frontend должен отражать предметную модель предприятия, а не структуру backend API.

Не создаются:

- универсальный CRUD framework;
- универсальный entity framework;
- универсальный dashboard framework;
- избыточный navigation framework.

Новые абстракции появляются только тогда, когда они подтверждены несколькими реальными сценариями.

## Consequences

### Positive

- оператор сразу попадает в рабочий контекст;
- интерфейс отражает организационную структуру предприятия;
- breadcrumbs становятся естественным способом навигации;
- полный организационный tree не перегружает стартовый экран;
- будущая authentication не требует изменения основной UX-модели.

### Negative

- необходимо определить текущий организационный контекст;
- сотрудники с несколькими назначениями требуют отдельного правила;
- требуется минимальный API текущего оператора.

## Architectural Principle

Интерфейс должен отвечать на два разных вопроса:

```text
Breadcrumbs:
Где я нахожусь?

Workspace:
Что я могу здесь делать?
```

Это разделение является основным UX-принципом Iteration 002.

## Main Question

Does this decision help us model the enterprise more accurately?

Да.

Рабочее пространство отражает положение конкретного оператора внутри организационной модели предприятия и не заменяет предметную структуру техническим набором страниц.
