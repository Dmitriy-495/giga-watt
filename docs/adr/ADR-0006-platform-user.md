# ADR-0006 — Platform User Model

## Status

Accepted

## Date

2026-08-15

## Context

Giga Watt переходит от технического Foundation к пользовательскому рабочему интерфейсу.

Для построения рабочего контекста оператора необходимо различать:

- сотрудника предприятия;
- пользователя Платформы.

`Employee` является сущностью предметной модели предприятия.

`User` является сущностью Платформы.

На текущем этапе не требуется полноценная authentication, система ролей или разрешений.

Необходимо ввести минимальную модель пользователя, достаточную для определения текущего оператора и его рабочего контекста.

## Decision

Ввести таблицу `users`.

Минимальный набор полей:

- `id`;
- `email`;
- `is_superuser`;
- `created_at`;
- `updated_at`.

Требования:

- `email` — `NOT NULL`;
- `email` — `UNIQUE`;
- `is_superuser` — `NOT NULL`;
- `is_superuser` — `DEFAULT false`.

Начальный пользователь Платформы определяется initial data как:

```text
tda
```

с признаком:

```text
is_superuser = true
```

Способ хранения идентификатора `tda` в модели User должен быть окончательно определён до реализации migration.

## User and Employee

`Employee` может существовать без `User`.

`User` в нормальном состоянии должен соответствовать `Employee`.

Сопоставление выполняется исключительно через таблицу:

```text
employee_emails
```

Алгоритм:

```text
users.email
    ↓
employee_emails.email
    ↓
employee_emails.employee_id
    ↓
employees.id
```

Поле `employees.email`, если оно существует, не используется как источник истины для данного сопоставления.

## Missing Employee

Отсутствие соответствующего сотрудника при создании пользователя не является основанием для блокировки создания User.

Система должна:

1. выполнить поиск в `employee_emails`;
2. создать User;
3. выдать предупреждение, если Employee не найден.

Таким образом, отсутствие Employee является диагностируемым состоянием приложения, а не обязательным database invariant.

## Ambiguous Match

Если один email соответствует нескольким Employee, результат считается неоднозначным.

Система не должна произвольно выбирать сотрудника.

Такое состояние должно быть диагностировано как ошибка качества данных.

## Database Relationship

На текущем этапе не создаётся обязательный внешний ключ:

```text
users → employee_emails
```

Причины:

- Employee может существовать без User;
- User может быть создан до появления Employee;
- отсутствие Employee является warning;
- связь определяется бизнес-правилом сопоставления email.

## Initial Data

Initial-data loader обязан поддерживать пользователей.

Пользователи загружаются после `employee_emails`.

Начальный пользователь `tda` должен импортироваться с:

```text
is_superuser = true
```

Правило сопоставления User → Employee при загрузке Excel должно быть тем же, что используется при создании пользователя в приложении.

## Authentication Scope

В рамках данного ADR не реализуются:

- passwords;
- login;
- sessions;
- JWT;
- OAuth/OIDC;
- registration;
- password reset;
- roles;
- permissions;
- полноценный authorization framework.

Эти вопросы относятся к отдельным будущим решениям.

## Consequences

### Positive

- появляется минимальная сущность пользователя Платформы;
- Employee и User остаются различными предметными сущностями;
- появляется основа для определения текущего оператора;
- frontend может строиться вокруг рабочего контекста;
- последующая authentication может быть добавлена независимо.

### Negative

- полноценной защиты доступа пока нет;
- User может временно существовать без Employee;
- сопоставление требует application-level проверки.

## Architectural Principle

Решение сохраняет разделение:

```text
Platform
    └── User

Enterprise
    └── Employee
```

и связывает их через существующую модель email сотрудников.

## Main Question

Does this decision help us model the enterprise more accurately?

Да.

User описывает участие человека в Платформе.

Employee описывает человека как часть предприятия.

Это разные аспекты одной реальной сущности и не должны смешиваться.
