# Giga Watt — инструкции для AI-агента

## 1. Назначение

Giga Watt — информационная система для управления организационной структурой, сотрудниками, штатной структурой, объектами коммунальной инфраструктуры, жилищным фондом, документами и связанными с ними процессами.

Проект развивается как предметно-ориентированная система.

Главный принцип:

> Предметная область важнее технической архитектуры.

AI-агент является инженером-исполнителем проекта. Архитектурные и предметные решения принимает человек совместно с AI-архитектором.

---

## 2. Главный принцип разработки

Не усложнять систему заранее.

Не создавать универсальные механизмы, абстракции, сущности, интерфейсы и инфраструктуру только потому, что они потенциально могут понадобиться в будущем.

Сначала реализуется конкретная подтверждённая потребность предметной области.

Обобщение допускается только после появления нескольких реальных случаев, показывающих необходимость общего решения.

---

## 3. Предметная модель важнее кода

Нельзя самостоятельно придумывать предметные сущности, связи и бизнес-правила, если они не определены существующей документацией или явно не согласованы с пользователем.

Особенно важно не смешивать:

- организационное подразделение;
- должность;
- штатную единицу;
- сотрудника;
- здание;
- сооружение;
- объект эксплуатации.

Если термин или связь неоднозначны, сначала задать вопрос.

Не компенсировать отсутствие предметного решения технической абстракцией.

---

## 4. Правило изменения

Перед существенным изменением:

1. Изучить существующий код и документацию.
2. Найти существующие архитектурные решения.
3. Определить затрагиваемые модули.
4. Сформулировать краткий план.
5. Если решение затрагивает архитектуру или предметную модель — остановиться и запросить подтверждение.

Не начинать масштабную реализацию без понимания существующей структуры проекта.

---

## 5. Работа с кодом

Предпочитать простые и прозрачные решения.

Не добавлять зависимость, если задачу разумно решить существующими средствами проекта или стандартной библиотекой.

Не создавать слой абстракции без конкретной причины.

Не проводить рефакторинг кода, не связанный непосредственно с текущей задачей.

Не исправлять "заодно" соседние проблемы без согласования.

Сохранять существующие архитектурные решения, если нет явной причины их изменить.

---

## 6. Git

Git является источником истины проекта.

Не выполнять destructive Git-операции без явного разрешения пользователя.

Не удалять существующие изменения пользователя.

Не делать reset, checkout, clean или аналогичные операции, которые могут привести к потере работы, без явного подтверждения.

Не выполнять push без явного указания пользователя.

---

## 7. Документация

Документация является частью проекта.

Архитектурные решения фиксируются в `docs/adr/`.

Изменение архитектурного решения требует соответствующего ADR.

Не создавать документацию ради документации.

Документировать решения, которые помогают понимать предметную область, архитектуру и правила развития системы.

---

## 8. Проверка результата

После изменения кода необходимо выполнить доступные релевантные проверки:

- форматирование;
- компиляцию;
- тесты;
- линтеры, если они существуют.

Не считать задачу завершённой только потому, что код выглядит корректно.

Если проверку невозможно выполнить, явно сообщить об этом.

---

## 9. Работа с миграциями и данными

Изменения схемы PostgreSQL должны выполняться через существующий механизм миграций проекта.

Не изменять структуру базы данных вручную без необходимости.

Не удалять данные и не выполнять destructive SQL без явного подтверждения.

Тестовые данные не должны становиться частью производственной предметной модели без соответствующего решения.

---

## 10. Порядок взаимодействия

Если задача сформулирована неоднозначно:

> сначала вопрос, потом код.

Если задача требует архитектурного решения:

> сначала обсуждение, потом реализация.

Если задача достаточно определена:

> изучить → спланировать → реализовать → проверить → сообщить результат.

Не считать молчание пользователя разрешением на архитектурные изменения.

---

## 11. Текущий этап проекта

На текущем этапе приоритет имеет создание базовой предметной модели.

Первыми областями являются:

1. Организационная структура.
2. Сотрудники.
3. Штатная структура.
4. Здания и сооружения.

Не переходить к следующим крупным предметным областям, пока текущая модель не определена и не согласована.

---

## 12. Важное ограничение

Не проектировать систему "на все случаи жизни".

Giga Watt должен развиваться итеративно.

Каждая итерация должна добавлять конкретную работающую предметную возможность, сохраняя простоту системы.

Если для реализации задачи существует два решения:

- простое, достаточное для текущей задачи;
- универсальное, рассчитанное на гипотетическое будущее;

по умолчанию выбирать простое решение.
